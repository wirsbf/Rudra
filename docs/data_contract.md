# 数据接口契约 (Data Contract)

本文档定义 `Rudra` 当前代码库中**跨模块传递的核心数据实体、边界输入输出、不变式与责任归属**。  
目标不是描述“理想中的完整反编译器”，而是约束**当前仓库可见实现**中的真实主干链路，减少模块之间的语义漂移、隐式假设和文档失真。

---

## 1. 适用范围

本契约适用于以下目录和模块之间的数据交互：

- `src/binary/`
- `src/disasm/`
- `src/pcoderaw.rs`
- `src/funcdata.rs`
- `src/op.rs`
- `src/varnode.rs`
- `src/block.rs`
- `src/heritage.rs`
- `src/action.rs`
- `src/coreaction.rs`
- `src/ruleaction.rs`
- `src/printlanguage.rs`
- `src/printc.rs`
- `src/type_system/`
- `src/align/`

不适用于：

- 仅用于实验、调试、临时输出的脚本文件
- 尚未真正接入主链路的历史/占位 API
- README 中存在但代码中暂未稳定暴露的最终用户接口

---

## 2. 总体流水线边界

当前主干应按如下抽象理解：

```text
二进制输入
  -> binary/disasm
  -> 原始 P-code 序列（PcodeOpRaw）
  -> Funcdata 内部图模型
  -> Basic Block / Control Flow 信息
  -> SSA / Heritage / ActionDatabase 变换
  -> 类型与变量语义补充
  -> PrintLanguage / PrintC 输出
```

### 2.1 每一层的职责边界

| 阶段 | 主要输入 | 主要输出 | 不应承担的职责 |
|------
|----------|----------|----------------|
| 二进制解析 | 文件字节、节区、符号信息 | 可反汇编的程序片段、函数
入口、基础元信息 | 不
直接生成高层 C 语义 |
| 反汇编/提升 | 机器指令 | `PcodeOpRaw` 序列 | 不做最终变量
命名 |
| 图模型构建 | `PcodeOpRaw` | `Funcdata`、`PcodeOp`、`Varnode`、Block 图 | 不做最终格式化输出 |
| SSA / Action | `Funcdata` 图 | 经过规则重写后的稳定 IR | 不
直接决定最终文本文风
 |
| 类型/变量恢复 | IR + 数据流信息 | 更丰富的类型与变量语义 | 不篡改底层地址事实 |
|
 代码生成 | 稳定 IR + 类型/变量语义
 | C 风格
文本 | 不回
写并改变分析真相 |

## 4. 核心实体契
约

## 4.1 `Address`

### 语义
`Address` 是所有跨模块定位的基础单位。它必须表达：

- 所属地址空间
- 空间内偏移
- 可用于排序、比较、显示和关联图节点

### 必须满足
1. 同一 `AddressSpace` 内的 `offset
` 才具有直接数值比较意义。
2. 不允许把不同空间的地址
当作统一线性地址解释。
3. `Address` 一旦用于 `SeqNum`、`Varnode` 或 block 边界后，不应被就地篡改语义。

### 禁止事项
- 把寄存器空间地址当作 RAM 虚拟地址打印给上游。
- 仅用裸 `u64` 代替需要区分空间的地址语义。

---

## 4.2 `SeqNum`

### 语义
`SeqNum` 是 `PcodeOp` 的稳定锚点，用来标识：

- 该操作对应的机器指令地址
- 同一地址下的局部顺序
- 必要时的时间/顺序信息

### 契约要求
1. `SeqNum` 对单个函数内的操作序必须可重复构建。
2. 在同一 `Funcdata` 中，`SeqNum` 应尽量保持唯一。
3. 后续优化/重写可改变图连接，但不应随意抹掉原始时序锚点。

### 作用边界
- `SeqNum` 是分析定位工具，不等价于源码行号。
- `SeqNum` 不负责表达控制流边。

---

## 4.3 `AddressSpace`

### 语义
`AddressSpace` 用于区分存储域，常见包括：

- RAM / memory
- register
- unique
- const
- stack（若以独立空间建模）
- join / other internal spaces（若实现存在）

### 契约要求
1. 所有 `Varnode` 必须绑定明确地址空间。
2. `unique` 空间只表示内部临时值，不应被直接伪装成用户变量。
3. `const` 空间中的值应被解释为立即数语义，而非普通内存引用。

### 输出约束
- 代码生成阶段可以把某些空间映射为高层语义，但不能改写其内部事实来源。
- 如果无法恢复高层变量，保留空间语义优于虚构变量名。

---

## 4.4 `Varnode`

### 语义
`Varnode` 是 P-code IR 中最小的数据承载单元，表达：

- 位置（空间 + offset）
- 大小
- 定义/使用关系
- SSA 版本信息（若已进入 SSA 阶段）

### 输入契约
`Varnode` 创建时至少应具备：

- 有效地址或等价空间定位
- 明确字节大小
- 合法的来源语义（const / register / unique / memory 等）

### 输出契约
进入后续阶段后，`Varnode` 应可支撑：

- def-use 关联
- 类型附着或类型推断入口
- 命名恢复候选
- 打印阶段的可显示身份

### 不变式
1. `size > 0`
2. 常量 `Varnode` 不应被当成普通可写存储
3. 若一个 `Varnode` 处于 SSA 态，其版本号必须在当前函数上下文内自洽
4. `Varnode` 与定义它的 `PcodeOp` 之间的关系必须可追踪

### 禁止事项
- 把多个不同定义点的 SSA 值直接合并成一个未标识版本的节点
- 在打印阶段反过来修改 `Varnode` 的底层事实以迎合文本样式

---

## 4.5 `PcodeOpRaw`

### 语义
`PcodeOpRaw` 是反汇编/提升阶段产出的**原始操作记录**，位于“机器指令语义”与“稳定图 IR”之间。

### 最低字段语义
一个原始操作至少应表达：

- `OpCode`
- 输入若干
- 输出（可选）
- 关联地址/顺序信息
- 必要时的行为或附加元数据

### 契约要求
1. `PcodeOpRaw` 必须尽可能忠实反映 lifting 结果，不提前掺入高层格式偏好。
2. 从 `PcodeOpRaw` 注入 `Funcdata` 时，必须保留操作顺序。
3. 不允许在此层静默吞掉无法解释的输入输出；若无法表达，应显式报错或记录缺失。

### 边界说明
- `PcodeOpRaw` 不是最终分析结构。
- 其职责是“可注入”“可复现”，不是“适合直接打印成 C”。

---

## 4.6 `PcodeOp`

### 语义
`PcodeOp` 是进入 `Funcdata` 后的正式 IR 操作节点，承担：

- 操作语义
- 输入/输出连接
- 与 `SeqNum`、Block、def-use 的关联
- 被规则系统访问和改写

### 契约要求
1. 每个 `PcodeOp` 必须有明确 `OpCode`。
2. 输入列表顺序必须保留语义意义。
3. 输出若存在，必须与节点生命周期一致。
4. 图变换后不得留下悬空输入或输出引用。

### 修改规则
- Action / Rule 可以改写 `PcodeOp`
- 但必须保证图在变换后仍然可遍历、可打印、可分析
- 对“已死”操作的标记与销毁必须一致，不能一半删除一半保留引用

---

## 4.7 `OpCode`

### 语义
`OpCode` 是跨模块共享的操作语义字典。

### 契约要求
1. `OpCode` 是语义源，不允许仅依赖字符串比较判断操作含义。
2. 所有分析、规则、打印逻辑都应优先基于 `OpCode` 分支。
3. 若与 Ghidra 对齐，需要保持枚举语义映射稳定。

### 演进规则
- 新增 `OpCode` 时，需同步考虑：
  - 原始 lifting
  - 图注入
  - 分析规则
  - 打印策略
  - API 文档

---

## 4.8 `BlockBasic` / CFG 相关实体

### 语义
控制流块表示函数级控制流结构，用于：

- 划分基本块
- 建立前驱/后继
- 支撑支配关系、循环识别与结构化输出

### 契约要求
1. 一个 block 应包含有序操作区间或等价引用。
2. 控制流边必须与终结指令/跳转语义一致。
3. block 划分完成后，SSA、Heritage、结构化打印不得各自私建冲突 CFG。

### 允许差异
- 中间分析阶段可附加辅助边或注释
- 但不得破坏主 CFG 的单一真相来源

---

## 4.9 `Funcdata`

### 语义
`Funcdata` 是单个函数的总分析上下文，也是当前主链路的核心交换容器。

### 应承载的内容
通常包括但不限于：

- 函数名 / 入口地址
- `PcodeOp` 集合
- `Varnode` 集合
- block / CFG 信息
- 函数原型信息
- 各类分析中间状态
- 与打印相关的恢复结果

### 核心契约
1. `Funcdata` 是**单函数边界**，不应混入多个函数的 IR。
2. 所有后续 Action/Rule 默认在 `Funcdata` 内部完成。
3. `Funcdata` 必须允许从 raw p-code 构建，并被逐步增强，而非一次性要求所有信息齐备。
4. `Funcdata` 内的对象引用关系必须可维护，不能在变换后出现银行/图状态失配。

### 生命周期契约
- 创建：函数入口已知，允许信息不完整
- 注入：raw p-code / varnode / op 图逐步建立
- 分析：CFG、SSA、类型、变量等逐层添加
- 输出：允许打印阶段读取，但不应由打印阶段主导核心分析真相

---

## 4.10 `FuncProto` / `ProtoParameter`

### 语义
描述函数级签名信息，包括：

- 返回值类型
- 参数列表
- 调用约定或近似约束
- 命名/显示辅助信息

### 契约要求
1. 原型若为推断结果，必须允许“不完整”状态。
2. 原型的恢复不应伪装成已确认事实。
3. 外部库函数和当前函数的签名来源应能区分：
   - 符号/导入已知
   - ABI 约定推断
   - 使用上下文推断
   - 暂未知

### 输出约束
最终代码生成可用原型改善输出，但如果原型可信度不足，应保守输出。

---

## 4.11 `Datatype`

### 语义
`Datatype` 是统一类型系统中的基础类型对象，用于承载：

- 原始整数/浮点/布尔
- 指针
- 数组
- 结构体
- 其他聚合或元类型

### 契约要求
1. 类型系统必须允许“未知类型”存在。
2. 类型传播不能伪造不存在的精确信息。
3. 结构体字段恢复若仅凭偏移启发，应允许保留通用字段名而不是冒充真实源码名。
4. 类型是语义增强层，不应否定底层 IR 的地址/数据流事实。

---

## 4.12 `ActionDatabase` 与规则系统

### 语义
`ActionDatabase` 是对分析/重写步骤的组织入口，负责把多个 Action / Rule 按顺序应用于 `Funcdata`。

### 契约要求
1. 输入必须是可分析的 `Funcdata`。
2. 输出必须仍是结构一致、可继续处理的 `Funcdata`。
3. 每个 Action/Rule 必须假设输入可能不完美，但不能默默破坏图。
4. 顺序敏感的规则应在文档或实现中体现依赖关系。

### 不允许
- 为了“看起来输出更漂亮”直接篡改核心事实
- 在失败时部分修改对象又不回滚，也不留下可诊断状态

---

## 4.13 `PrintLanguage` / `PrintC`

### 语义
输出层负责把内部分析结果转成可阅读文本，`PrintC` 是面向 C 风格输出的主要实现。

### 输入契约
应依赖以下数据：

- 稳定的 `Funcdata`
- 尽可能完整的 block / CFG
- 类型/变量恢复结果
- 函数原型信息

### 输出契约
输出文本应尽量满足：

- 可读
- 结构化
- 不伪造超出分析依据的信息
- 尽量保持与内部语义一致

### 允许的保守行为
当无法恢复高级语义时，可以：

- 使用通用变量名
- 保留较低层表达
- 输出近似伪代码而非“假装完整源码”

### 禁止事项
- 仅为美观删除有语义意义的副作用
- 把尚未验证的类型/控制流当成确定结论输出

---

## 5. 阶段间 I/O 契约

## 5.1 二进制解析 -> 反汇编/提升

### 输入
- 原始二进制字节
- 文件格式元信息
- 节区 / 段 / 符号表
- 可选导入导出信息

### 输出
- 可定位的指令流
- 函数入口或候选代码区域
- 与地址空间映射相关的基础信息

### 不变式
- 文件格式解析错误必须显式报错
- 地址映射必须与后续 `Address` 语义兼容

---

## 5.2 反汇编/提升 -> `PcodeOpRaw`

### 输入
- 已解码机器指令
- 架构语义
- 操作数与地址信息

### 输出
- 有序 `PcodeOpRaw` 序列

### 契约要求
1. 同一机器指令可产生多条 raw p-code。
2. 输出顺序必须稳定。
3. 若部分指令尚不支持，应显式暴露支持缺口，而不是静默跳过。

---

## 5.3 `PcodeOpRaw` -> `Funcdata`

### 输入
- 原始操作序列
- 函数入口信息
- 可选符号/原型信息

### 输出
- 建立好的 `Funcdata`
- 绑定完成的 `PcodeOp` / `Varnode`
- 初步 block 边界信息

### 契约要求
1. raw 序列中的输入输出必须映射到图对象。
2. 必须建立操作与地址/顺序锚点。
3. 构建失败时，应优先报结构不一致，而不是生成半损坏图。

---

## 5.4 `Funcdata` -> CFG / SSA / Heritage

### 输入
- 可遍历的函数 IR
- block 初始划分
- def-use 可构建基础

### 输出
- 稳定控制流图
- SSA 版本信息
- Phi / multiequal 等结构（如实现存在）

### 契约要求
1. SSA 建立前后必须能解释同一函数语义。
2. 新增 Phi 节点时，来源和支配逻辑必须可追踪。
3. SSA 是语义敏感层，若无法保证一致性，应保守停留在较低阶段，而非伪造版本号。

---

## 5.5 分析/规则系统 -> 类型/变量恢复

### 输入
- 已稳定化的 IR
- SSA、CFG、def-use 等结果

### 输出
- 更高层的变量名、类型、结构体字段、函数原型等信息

### 契约要求
1. 推断结果必须可回溯到证据来源。
2. 启发式恢复应允许“不确定”。
3. 高层命名不能反向污染底层数据真实性。

---

## 5.6 分析结果 -> 代码生成

### 输入
- `Funcdata`
- block / 控制流结构
- 类型和变量信息
- 函数签名

### 输出
- C 风格文本或伪代码文本

### 契约要求
1. 代码生成是“表示层”，不是“事实制造层”。
2. 若某语义无法安全结构化，可退回更低层表达。
3. 输出应尽量与控制流和数据流一致，不得凭空重排副作用顺序。

---

## 6. 共享不变式

以下规则适用于整个主链路：

### 6.1 单函数隔离
任何 `Funcdata`、SSA、CFG、变量恢复结果都必须限定在单个函数上下文内。

### 6.2 引用完整性
所有图对象之间的引用必须可遍历、可验证、无悬空。

### 6.3 可降级但不可伪造
当恢复失败时，允许降级输出；不允许伪造高层信息。

### 6.4 保留来源信息
地址、顺序、原始操作语义应尽量保留到足以调试和对齐验证的程度。

### 6.5 对齐验证优先于主观美化
与 Ghidra 对齐相关的中间语义，不应为了更“好看”的文本输出而改变。

---

##
 7. 错误处理契约

### 原则
跨模块边界失败时，必须优先返回“可定位的上下文错误”，而不是吞错。

### 建议包含的信息
- 所在函数 / 地址
- 当前阶段
- 失败实体类型
- 期望与实际差异
- 是否为暂未实现 / 数据损坏 / 逻辑不一致

### 示例场景
- 无法把 raw p-code 注入图
- block 划分后出现悬空跳转
- SSA 重命名发现非法重复定义
- 打印阶段发现缺少必要类型/变量引用

---

## 8. 与 Ghidra 对齐的特殊约束

由于本项目显式受 Ghidra 启发，以下对象的语义稳定性具有更高优先级：

- `Address`
- `SeqNum`
- `Varnode`
- `PcodeOp`
- `Funcdata`
- `Heritage`
- `ActionDatabase`
- `PrintLanguage` / `PrintC`

### 对齐文档与验证边界
- 静态结构一致不等于运行时语义一致
- 有无 FFI/对拍能力，应在验证文档中如实说明
- “已支持”“已完成”“已验证”必须严格区分：
  - 已有代码实现
  - 已跑通样例
  - 已与 Ghidra 对比验证

## 11. 简明执行准则

如果你在修改代码时不确定某个数据该放在哪一层，请优先遵守以下判断顺序：

1. **这是底层事实，还是高层解释？**
   - 底层事实留在 IR / graph / address / varnode
   - 高层解释留在 type / variable / print

2. **这是单函数内部状态，还是跨函数信息？**
   - 单函数状态进入 `Funcdata`
   - 跨函数信息不要偷偷塞进单函数对象

3. **这是已知结论，还是启发式猜测？**
   - 已知结论可以固化
   - 猜测必须允许降级和保守输出

4. **这个变更会不会让输出更好看，但语义更不可信？**
   - 如果会，优先保留可信度

## 12. 结论

本数据契约的核心原则只有一句话：

**Rudra 的跨模块数据传递必须以“语义真实、边界清晰、可验证、可降级”为先，而不是以“看起来像完整反编译器”为先。**

只要坚持这一点，文档、实现、验证和输出质量才能逐步收敛，而不会继续失真。
