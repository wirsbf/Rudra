# `pcode/` API Reference（旧版 P-code 架构说明）

**源代码路径**: `src/pcode/`  
**当前状态**: **历史遗留 / 旧架构说明**  
**维护结论**: 本目录对应的是 Rudra 早期围绕 `Program` 容器组织的 P-code 架构文档入口。它可以帮助理解项目历史演化，但**不应再被当作当前主干架构的权威入口**。

---

## 1. 本文档的定位

`docs/api/pcode/mod.md` 用于说明 Rudra 中 **旧版 `pcode/` 架构** 的文档定位与使用边界。

它回答的是：

- 早期 `pcode/` 层试图解决什么问题
- `Program` 架构在项目中扮演过什么角色
- 为什么今天仍保留这部分文档
- 为什么现在不能再把它当作当前主线 API 入口

它**不负责**证明以下内容：

- 当前 `src/` 仍以 `pcode/Program` 为核心组织
- 当前端到端反编译主线仍依赖旧 `Program` 容器
- 当前 CLI、输出链路或验证链路已经围绕该架构完整打通
- 旧文档所描述的全部能力今天仍可直接使用

---

## 2. 历史背景

Rudra 在较早阶段曾更明显地采用一套“独立 `pcode/` 层”的组织思路，核心特点包括：

- 用统一的 P-code 中间表示承接机器指令语义
- 用 `Program` 作为操作集合和中间状态的主要容器
- 让后续分析、优化和代码生成围绕该容器展开
- 将架构无关语义与机器指令层解耦

在这个阶段，`pcode/` 文档主要承担以下作用：

1. 说明 P-code 层的对象组织方式  
2. 给旧分析模块提供统一的输入容器  
3. 作为从 lifting 走向优化与输出的桥梁  

这套设计在项目早期具有明确价值，因为它让反编译流程更容易从“指令级语义”过渡到“可分析的中间表示”。

---

## 3. 为什么它现在被视为“旧架构说明”

结合当前 Rudra 可见源码与总控文档，项目主干已经更明显地收敛到以下方向：

- 围绕 `Funcdata` 组织单函数分析上下文
- 使用 `PcodeOp` / `Varnode` / block / heritage 等对象直接构图
- 通过 `ActionDatabase` 驱动分析与变换
- 逐步向 Ghidra 风格核心对象模型对齐
- 让输出层围绕 `PrintLanguage` / `PrintC` 工作

因此，今天再看 `pcode/`，更准确的定位应该是：

> 它代表 Rudra 早期的 P-code 容器化思路，尤其是围绕 `Program` 的旧架构。  
> 这部分内容对理解历史设计仍有帮助，但已经不适合作为当前主线架构的第一入口。

### 4.1 可以把它当作什么
你可以把 `pcode/` 文档当作：

### 4.2 不应把它当作什么

- 当前端到端反编译主线的准确总览
- 当前输出链路、验证链路、CLI 链路的权威说明

---

## 5. 旧版 `Program` 架构的核心思路

在旧架构中，`Program` 的角色大致可以理解为：

- 持有一组 P-code 操作
- 管理操作的顺序与唯一标识
- 记录入口点
- 作为后续分析与输出的输入对象
- 为旧版分析模块提供统一容器

这种方式的优势在于：

- 容易把“P-code 序列”集中管理
- 便于早期快速实现分析流程
- 对从反汇编到高级语义的分层有帮助

但它也有局限：

- 难以完全对齐 Ghidra 风格的对象组织方式
- 对复杂分析状态的承载能力有限
- 不如 `Funcdata` 体系那样天然贴合函数级全局上下文
- 在与 block、heritage、Action 系统深度联动时，扩展成本更高
