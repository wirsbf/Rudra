## 模块定位

`binary/mod.rs` 是 Rudra 当前的**二进制解析与加载入口层**。  
它的主要职责是：

1. 识别并解析二进制文件格式
2. 提取后续分析所需的基础元信息
3. 为反汇编、符号查询、字符串读取等后续阶段提供访问入口
4. 将“原始文件字节”转换成“可供程序分析使用的已解析对象”

从整体链路来看，它大致位于：

```text
raw binary bytes
  -> binary::Binary::parse(...)
  -> format / architecture / entry point / symbols / sections
  -> disasm
  -> raw semantics / IR
  -> Funcdata / Action / PrintC
```

因此，`binary` 模块应被理解为：

- **输入解析层**
- **文件格式抽象层**
- **后续分析的数据源提供者**

而不是：

- 最终反编译结果生成器
- 输出层
- 类型恢复层
- 完整用户产品入口

---

## 当前支持范围的正确表述

从当前模块说明和工程整体结构来看，`binary` 层的目标是覆盖常见可执行文件格式，包括：

- ELF
- PE
- Mach-O

但更准确、也更符合当前文档基线的表述应当是：

> 当前 `binary` 模块承担“多格式二进制解析”的架构职责，文档中提到 ELF / PE / Mach-O 方向支持；  
> 具体支持深度、样本覆盖范围和与后续主链路的稳定集成程度，应以实际源码、测试与状态文档为准，而不应由 API 文档单独夸大。

因此，后续引用该模块时建议使用：

### 推荐表述
- “`binary` 是 Rudra 的二进制解析与加载层”
- “它为后续反汇编与分析提供基础元信息”
- “目标覆盖 ELF / PE / Mach-O 等常见格式”
- “具体支持深度应以当前实现和验证结果为准”

### 不推荐表述
- “Rudra 已完整支持所有主流二进制格式”
- “有 `Binary::parse()` 就代表产品已经成熟可用”
- “二进制输入层已经完全稳定，无需继续验证”
- “只要能 parse，就说明后续反编译质量已有保障”

## 与其他模块的关系

### 与 `disasm/` 的关系
`binary` 负责把文件格式、架构、地址映射等基础信息组织出来；  
`disasm` 则负责在这些信息基础上，把机器码解码成指令表示。

可以简化理解为：

- `binary`: “这是什么文件、里面有什么、入口在哪、有哪些函数/字符串/符号”
- `disasm`: “从这些地址和字节中能解码出什么指令”

### 与 `funcdata.rs` 的关系
`funcdata` 是函数级分析容器；  
`binary` 不是直接做函数分析，而是为 `funcdata` 相关流程提供输入背景，例如：

- 函数入口地址
- 函数名
- 字符串字面量
- 架构信息

### 与 `printc.rs` 的关系
`binary` 不负责输出 C-like 文本。  
它提供的是底层输入事实，而不是高层文本表达。

### 与 `align/` 的关系
若未来进行更严格的运行时对拍，`binary` 层可能是验证链条中的上游输入点之一。  
但当前不应把它写成“已完成与 Ghidra 的二进制解析一致性验证”。

## 导出的公共 API

以下说明围绕当前文档中可见的公开接口展开，重点解释它们在“解析层”中的角色。

---

## `pub enum BinaryFormat`

表示二进制文件格式类型。

### 角色
这是 `binary` 模块中用于表达“当前文件属于哪种格式”的基础枚举类型。

### 典型用途
- 区分 ELF / PE / Mach-O
- 调试输出
- 上游或下游按格式分支处理
- 日志、报告与状态显示

### 应如何理解
`BinaryFormat` 只回答“文件格式是什么”，不回答：

- 这个格式支持得是否完整
- 这个样本是否已通过全部测试
- 这个格式在后续反汇编和输出层中是否已完整打通

---

## `pub struct Binary`

表示已经解析完成的二进制文件对象。

### 角色
这是 `binary` 模块的核心类型，可以理解为：

> “一个已经从原始字节中解析出来、可供后续分析访问的二进制对象”

它通常会承载或提供以下能力：

- 文件格式信息
- 架构信息
- 入口点
- 函数地址列表
- 函数名查询
- 字符串读取
- 供反汇编层读取函数内容的入口

### 当前应如何理解
`Binary` 不是最终反编译器的高层 façade，也不是“拿来即用”的完整产品对象。  
它更像是 Rudra 当前输入层中的**核心解析结果容器**。

---

## `pub fn parse(data: &[u8]) -> Result<Self>`

从原始字节解析一个二进制文件。

### 作用
这是 `binary` 模块最重要的入口函数之一，用于把文件字节转换成 `Binary` 对象。

### 参数
- `data`: 原始二进制字节

### 返回
- 成功时返回一个 `Binary`
- 失败时返回错误

### 工程意义
这一步的作用是把“不可直接分析的原始文件字节”变成“可以进一步访问入口点、架构、函数和字符串等信息的对象”。

### 注意事项
`parse(...)` 成功只说明：

- 文件格式被识别并解析到了某个可用层次
- 返回了可继续分析的对象

它**不等于**：

- 文件的所有细节都已完整建模
- 反汇编一定会成功
- 反编译一定会成功
- 输出质量一定可靠

---

## `pub fn entry_point(&self) -> Address`

获取二进制入口点地址。

### 作用
返回当前二进制对象的入口点。

### 典型用途
- 调试显示
- 初始分析起点
- 与程序装载逻辑关联
- 为进一步探索代码区域提供起点

### 注意事项
入口点是文件级入口，不等于：

- 你真正想分析的业务函数
- 某个特定用户函数
- 最终反编译输出的唯一入口

---

## `pub fn format(&self) -> BinaryFormat`

获取二进制格式。

### 作用
返回当前文件属于哪种 `BinaryFormat`。

### 典型用途
- 显示格式信息
- 做格式分支
- 调试与日志记录

### 说明
该接口主要提供格式级元信息，不应被过度解读为“格式支持度证明”。

---

## `pub fn architecture(&self) -> Architecture`

获取目标架构。

### 作用
返回当前二进制所属的目标架构。

### 典型用途
- 创建对应架构的反汇编器
- 后续语义提升
- 指令语义分支
- 调试输出

### 注意事项
返回架构信息只说明“当前文件被识别为某种架构”，不等于：

- 该架构当前在 Rudra 中已完整支持
- 所有该架构指令都能正确 lifting
- 对该架构的最终 C-like 输出已经成熟

---

## `pub fn get_functions(&self) -> Vec<Address>`

获取函数地址列表。

### 作用
返回当前二进制中可识别的函数入口地址集合。

### 典型用途
- 枚举候选函数
- 选择函数做反汇编或分析
- 与符号表、导入导出、样本验证数据做关联

### 返回值语义
返回一个函数入口地址列表。

### 注意事项
这个接口的存在不应被写成：

- “函数识别已经完全准确”
- “所有函数都已可靠恢复”
- “后续反编译将自动完整成功”

它更适合作为“当前解析层给出的函数候选入口集”。

---

## `pub fn get_function_name(&self, addr: Address) -> Option<&String>`

按地址获取函数名。

### 作用
查询某个函数地址是否存在已知名称。

### 典型来源
名称可能来自：

- 符号表
- 导出表
- 调试信息
- 解析层恢复的函数命名信息

### 返回值
- `Some(name)`: 当前地址存在已知函数名
- `None`: 没有已知名称

### 注意事项
返回 `Some(...)` 不自动意味着：

- 这个名称一定是源码原名
- 后续分析会完整利用这个名称
- 这个名字在输出层一定最终稳定呈现

---

## `pub fn read_string_at(&self, addr: Address) -> Option<String>`

从给定地址读取 null-terminated 字符串。

### 作用
尝试从二进制对象中读取指定地址处的字符串内容。

### 典型用途
- 字符串字面量恢复
- 调试输出
- 输出层把地址常量显示成可读字符串
- 调用语义辅助判断

### 返回值
- `Some(text)`: 成功读取到字符串
- `None`: 该地址未能读取出字符串

### 注意事项
能读取字符串说明当前解析层具备一定的数据访问能力，但不等于：

- 所有字符串都能恢复
- 所有字符串编码都已处理
- 最终输出层已经完整整合所有字符串恢复逻辑

## 已移除：`pub fn disassemble_function`（2026-09-26，SLEIGH-RUSTIFY-PHASE3-0001）

该桥接接口随 iced-x86 退役一并删除。它只服务于 `lib.rs` 中已被注释停用的
`Decompiler` 旧壳（`generate_pcode` 死代码），生产解码路径（canon 驱动、CLI
预扫描、Funcdata 测试站点）从不经过它。函数级解码现在由
`disasm::sleigh_lift` 的线性 SLEIGH walk 直接从字节窗口构建
`PcodeOpRaw`，不再有“binary 层发起反汇编”的中间桥。

## 风险与限制提示

### 1. 二进制解析成功不等于后续全部成功
`Binary::parse(...)` 成功，只代表输入层已经建立，不代表后续反汇编、lifting、SSA、打印全部可用。

### 2. 格式支持不等于样本覆盖充分
即使文档列出了 ELF / PE / Mach-O，也不应自动推导出所有变体、所有边界条件都已成熟支持。

### 3. 函数列表不等于函数恢复准确率证明
`get_functions()` 返回的是当前解析层给出的函数入口集合，不应被直接视作完整准确恢复结果。

### 4. 输入层不替代验证层
`binary` 层是主链路基础，但它本身不能证明 Rudra 已达到与 Ghidra 等价的产品成熟度。
