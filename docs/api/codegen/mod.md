# `codegen/` API Reference（历史层说明）

**源代码路径**: `src/codegen/`

## 文档状态

**状态**：⚠️ 历史文档 / 待校准  
**可信度**：低到中  
**适用范围**：仅用于说明 Rudra 曾经存在或规划过的旧式 `codegen` 分层，不应被当作当前主线实现的权威入口。

---

## 1. 这份文档为什么需要重写

当前 `rudra` 仓库中的源码主线，已经不再以一个稳定、独立的 `src/codegen/` 目录作为最终代码生成层来组织。  
因此，旧文档里把 `codegen/` 描述成“当前正式 C 代码生成后端”的说法，会制造明显失真。

更准确的表述应该是：

- `codegen/` 代表的是**历史分层概念**或**旧架构残留文档分区**
- 当前可见实现中，面向输出的主线更接近：
  - `src/prettyprint.rs`
  - `src/printlanguage.rs`
  - `src/printc.rs`
- 若旧文档中出现 `generate_c_code(...)`、`FunctionAnalysis`、`Program` 等组合，应优先视为**旧架构说明**，而不是当前稳定 API

---

## 2. 当前应如何理解 `codegen/`

`codegen/` 在文档层面可以理解为：

> Rudra 早期或历史架构中，用于承载“分析结果 → C 风格输出”的分层概念。

它说明项目曾试图把“代码生成”单独抽象成一个后端层，接受类似：

- `FunctionAnalysis`
- `Program`
- `Binary`

这样的分析结果输入，然后输出结构化 C 代码。

但按当前仓库状态，这套分层**不应再被当作现行主线**。

---

## 3. 当前主线中的替代位置

如果你现在要理解 Rudra 的输出层，应该优先查看这些真实存在且更贴近当前主线的模块：

### `src/prettyprint.rs`
负责格式化输出相关的基础设施。

### `src/printlanguage.rs`
负责输出语言层抽象，是更接近“语言无关打印接口”的位置。

### `src/printc.rs`
负责 C 风格输出，是当前最应优先阅读的“代码生成 / 文本输出”实现入口。

---

## 4. 为什么旧 `codegen` 文档有风险

旧 `codegen` 文档如果不加说明，容易造成以下误解：

1. 误以为当前仍存在稳定的 `src/codegen/` 主实现目录
2. 误以为 `generate_c_code(...)` 仍是当前正式主入口
3. 误以为旧版 `FunctionAnalysis + Program` 架构仍是当前主分析链路
4. 误以为 Rudra 当前的输出后端已经按旧文档方式完整可用

这些判断都不应直接成立。

---

## 5. 历史层可能描述过的内容

旧 `codegen` 分层通常涉及以下概念：

- 函数签名生成
- 局部变量声明生成
- 控制流结构化输出
- 表达式格式化
- 字符串字面量恢复
- 基于分析结果的 C 风格代码拼接

这些内容作为“设计方向”仍然有参考价值，但是否仍由独立 `codegen/` 层实现，必须以当前源码为准。
